# CQRS: устройство и границы

Как в проекте разделены чтение и запись расписания, кто чем владеет и где это разделение
протекает.

**Актуальные контракты эндпоинтов** — в [API_EXAMPLES.md](API_EXAMPLES.md).
**Схема таблиц** — в [DATABASE.md](DATABASE.md).
**Задачи и техдолг** — в [FOLLOWUPS.md](FOLLOWUPS.md).

## Зачем разделение

Расписание читают несопоставимо чаще, чем меняют, и читают денормализованно (сетка «день × пара»
с именами преподавателей, групп, аудиторий). Писать же нужно консистентно, с валидацией ресурсов
и подбором аудиторий через доменное ядро солвера. Это две разные модели данных, и попытка обслужить
их одной сущностью упирается либо в тяжёлые JOIN на чтении, либо в денормализацию на записи.

Поэтому:

**Command Side (запись)** — `schedule_session` → `lesson_placement` (+ `placement_auditoriums`).
Нормализовано, с аудитом (`created_by`/`updated_by`) и версией сессии. Здесь живут генерация,
перенос, ручная раскладка, пины, очистка.

**Query Side (чтение)** — `schedule_view`: одна строка = одно занятие **для одной группы**,
все имена денормализованы, индексы по дате/преподавателю/группе/аудитории. Отсюда кормится сетка
(`GET /query/all`) и отчёты.

**Синхронизация** — событиями: `ScheduleGeneratedEvent` / `PlacementChangedEvent` (изменилось само
размещение) и `ProjectionStaleEvent` (изменились master-данные, снимок которых размещение несёт) →
`ScheduleSynchronizer` (`@Async`, `AFTER_COMMIT`) — единственный, кто пишет в `schedule_view`.

```
       команда                              событие (@Async, AFTER_COMMIT)
HTTP ──────────► Command Side ──────────────────────────► Query Side ──────► HTTP
                 schedule_session                          schedule_view      (сетка,
                 lesson_placement                                              отчёты)
                 (валидация через ScheduleWorkspace)
```

## Живые точки входа

| Сторона | Класс | Базовый путь |
|---|---|---|
| Command | `ru.controllers.command.ScheduleCommandController` | `/api/schedule/command/...` |
| Query | `ru.controllers.read.ScheduleQueryController` | `/api/schedule/query/...` |
| Подбор вариантов переноса | `ru.controllers.ScheduleMoveController` | `/api/schedule/find-move-options` (**без** `/command`) |
| Живые обновления (SSE) | `ru.controllers.read.ScheduleStreamController` | `/api/schedule/query/stream/{sessionId}` |

Валидация любой мутации проходит через один и тот же доменный примитив —
`ScheduleWorkspace.findPlacementOption` (тот же, что использует генератор). Поэтому подсказка
(«куда можно перенести») и фактический перенос не могут разойтись в проверках: аудиторию подбирает
бэк, с фронта она не принимается.

## Инварианты read-модели: кто чем владеет (2026-07-13)

Проекция производна от write-стороны, но **write-сторону меняет не только код, а ещё и сама БД**:
`ON DELETE CASCADE` сносит `lesson_placement` мимо Hibernate, мимо событий, мимо приложения. Пока
знание «у размещения есть проекция» было размазано по сервисам удаления, находились пути, где о нём
забывали, — и в расписании оставались **занятия-призраки**. Отсюда два разных инварианта и два
разных владельца.

### Инвариант 1 — строка проекции не переживает своё размещение. **Владелец: схема БД**
`schedule_view.placement_id` → FK на `lesson_placement` с `ON DELETE CASCADE` (миграция 017).
Сирота стала физически невозможной — кто бы ни удалил размещение: каскад дисциплины/курса/слота/
назначения/сессии, будущий код или ручной SQL. Следствие для кода: **сервисы удаления не чистят
`schedule_view` руками** (эту чистку убрали из `AssignmentService` и `CourseDeletionService` — там
она дублировала схему и была неполной).

### Инвариант 2 — снимок в строке не врёт. **Владелец: код**
`schedule_view` денормализует имена преподавателя/группы/аудитории/дисциплины, тему и вид занятия.
FK тут бессилен: размещение живо, врёт содержимое. Схема:

```
мутатор master-данных                 ProjectionMaintenance          ScheduleSynchronizer
(Educator/Group/StudyStream/   ──►    .announce(source, ids)   ──►   .onProjectionStale
 Auditorium/Discipline/Theme/          (единая дверь, Facade)         (единственный писатель
 CurriculumSlot/Assignment)             │                              schedule_view)
                                        └─ ProjectionSource (Strategy как enum):
                                           «от сущности → к затронутым размещениям»
```

- **Мутатор говорит, ЧТО изменилось, а не что чинить** — он не видит ни `ScheduleViewRepository`,
  ни событий (DIP). Новое денормализованное поле = новая константа `ProjectionSource` (OCP).
- **Событие несёт уже разрешённые id размещений**, а не id сущности. Это не оптимизация: часть
  источников устаревания — удаление (группу убрали из потока, аудиторию снесли), и после коммита
  связь «сущность → размещение» уже не существует. ⚠️ Отсюда правило: **при удалении объявлять ДО
  удаления**.
- Смена состава потока разрешается **по потоку**, а не по группе: выбывшую группу по ней не найти.

### Что в проекцию НЕ кладут — и почему это решение, а не недоделка
Подразделение преподавателя/группы (`org_unit`, 2026-07-21) в `schedule_view` **не
денормализовано** сознательно. Каждое денормализованное поле — это обязательство: переименование
кафедры обязано было бы порождать перепроекцию, то есть новую константу `ProjectionSource` и весь
её жизненный цикл. Разрез «расписание кафедры» этого не требует: бэк разрешает подразделение в
множества `educator_id`/`group_id` и фильтрует по уже существующим индексам.

Правило на будущее: **прежде чем добавить поле в проекцию, найдите его мутатора** и убедитесь, что
он готов объявлять устаревание. Если такого владельца нет — поле в проекции станет тихо врать.

### Проверка инвариантов — не в логе, а на дашборде
`GET /query/projection-health?periodId=` сверяет Command Side с Query Side: сколько размещений не
доехало до проекции. Сбой асинхронного слушателя раньше оставлял единственный след — строку в логе,
то есть не оставлял никакого. Теперь дашборд показывает баннер и кнопку «Восстановить отображение»
(`POST /command/sessions/{id}/reproject`, расписание не двигается).
Обратную сторону («строка есть, размещения нет») проверять не надо — её запрещает FK.

### Цена удаления называется заранее
Каскады уносят размещения молча и про `locked` ничего не знают, поэтому предпросмотр последствий —
часть тех же инвариантов: `/assignments/{id}/delete-impact`, `/discipline-courses/{id}` (preview),
`/auditoriums/{id}/delete-impact`, `/curriculum-slots/{id}/delete-impact`. Решение «удалять нельзя»
(`deletable`) считает **бэк** — фронт его показывает, а не выводит из чисел.

## Где разделение протекает (важно знать)

### ✅ Optimistic lock ПОЧИНЕН (2026-07-14) — было: не работал

**Что теперь.** Инвариант «мутация размещения = новое поколение агрегата» имеет одного владельца —
**`ScheduleSessionGate`** (`ru.services.session`): единая дверь «взять сессию на запись», которая
неразделимо делает сверку `expectedVersion` и `@Lock(OPTIMISTIC_FORCE_INCREMENT)`. Через неё проходят
**все** мутаторы размещений (перенос, цепочка, ручная установка/снятие, пин, пересортировка, очистка,
аддитивная генерация). Все команды несут `version`; конфликт → **409** `ConflictResponse` через
`CommandExceptionHandler` (`@RestControllerAdvice`) — исключение прилетает на КОММИТЕ, поэтому ловить
его в каждом эндпоинте было нельзя.

Заодно **перенос и пересортировка слиты в одну команду** (одна транзакция): раньше `reorder` был
вторым HTTP-запросом с фронта, и расписание успевало побывать в состоянии «перенесли, но не
пересортировали».

Подтверждено живым прогоном: два окна, перенос в первом (`74` → `75`), во втором — 409 с актуальной
версией. **Раньше второе окно молча затёрло бы работу первого.** Детали, ловушки и остаток —
в [FOLLOWUPS.md](FOLLOWUPS.md).

### ✅ Свежесть чтения: живой канал SSE (2026-07-14)

Оптимистичный лок защищает данные, но не рассказывает вкладке о чужих правках — раньше она узнавала
о них только получив 409. Теперь есть push:

```
мутация → commit → ScheduleSynchronizer пишет schedule_view → ScheduleProjectedEvent
                                                                      │ AFTER_COMMIT
                                                       ScheduleChangeNotifier → SseEmitter'ы
                                                       («звонок»: {sessionId, version})
```

- **`GET /api/schedule/query/stream/{sessionId}`** (`ru.services.stream`) — вкладка подписывается
  браузерным `EventSource`.
- **Событие шлётся ПОСЛЕ записи проекции** — это главное. По `PlacementChangedEvent` звонить нельзя:
  он наступает до неё, и клиент перечитал бы старые данные. Именно поэтому звонок **заменил
  `setTimeout(1000)`**: фронт больше не гадает, успела ли асинхронная проекция, — ему говорят.
- **Передаётся звонок, а не данные.** Что перечитать — решает клиент, обычными REST-эндпоинтами.
  Второй канал доставки данных неизбежно разошёлся бы с первым.
- Пачки событий клиент **схлопывает** (массовая очистка = сотни событий → одна перезагрузка).
- SSE, а не WebSocket: нужен односторонний поток, и он работает поверх обычного HTTP с
  автопереподключением. CRDT/OT — другой класс задач (одновременная правка одного объекта).

⚠️ **Граница:** реестр подписчиков — в памяти процесса. При нескольких инстансах мутация на узле A
не дойдёт до вкладок узла B; шину брать у PostgreSQL (`LISTEN`/`NOTIFY`), Redis не нужен.

### 🔴 Optimistic lock не работает
`ScheduleSession` имеет `@Version`, команды принимают `expectedVersion` и сверяют его — но мутаторы
меняют **`lesson_placement`**, а не строку `schedule_session`. Hibernate инкрементирует `@Version`
только при изменении самой строки сессии, поэтому версия **не растёт**, и проверка не срабатывает
никогда.

Сплошная вычитка (2026-07-14) уточнила картину: путей записи в `lesson_placement` **восемь**, а не
три. Версию поднимают **только генерационные** (`runGeneration`/`regenerateKeepingLocked`/
`generateCourseAdditive` — у них есть `updateStatus`). Не поднимают: `moveLesson`, `moveChain`,
`place`, `remove`, `setLock`, `resort` и — самое опасное — **`clearPlacements`**, который сносит
тысячу размещений, не сдвинув версию.

**Два следствия:**
- **Конкурентная защита декоративна** — двое, редактирующие одно расписание, молча затрут друг друга.
- **Версия как ключ кэша workspace хуже, чем бесполезна:** она меняется на генерации (где кэш и так
  сбрасывается) и молчит на очистке/переносе (где сброс обязателен). Плюс каскады БД сносят
  размещения **мимо приложения** — версия не заметит и этого, поэтому кэшу нужна ещё и подписка на
  `ProjectionStaleEvent`.

**Куда это чинить:** инвариант «мутация размещения = новое поколение агрегата» должен иметь одного
владельца — `ScheduleSessionGate` (единая дверь «взять сессию на запись»: сверка `expectedVersion` +
`OPTIMISTIC_FORCE_INCREMENT`), по образцу `ProjectionMaintenance`. Разложить `touch()` по восьми
мутаторам — значит повторить ошибку, из-за которой родились призраки: девятый путь про него забудет.
Полная карта, ловушки (`move`→`reorder`, фронт выбрасывает версию, `ScheduleManager` её не освежает)
и порядок шагов — в [FOLLOWUPS.md](FOLLOWUPS.md).

</details>

### ✅ Асинхронная проекция обгонялась фронтом — снято SSE (2026-07-14)
`schedule_view` по-прежнему обновляется после коммита, асинхронно, но фронт больше не гадает,
успела ли проекция: ему приходит звонок **после** записи (см. раздел выше). `setTimeout(1000)` в
`ScheduleManager` и переносе убраны — остались запасным путём на случай обрыва потока. В
планировщике замок и до этого работал на оптимистичном обновлении без гонки.

Из-за той же асинхронности «доска раскладки» сознательно читает **Command Side** напрямую: ей
нужны данные, синхронные с коммитом (и это решение SSE не отменяет).

### ⏳ `ScheduleSynchronizer.onScheduleGenerated` навигирует ленивые ассоциации
Работает с detached-сущностями из события — «по удаче». Правильно: перечитывать placement по id в
своей транзакции и звать общий `syncPlacementViews`, как уже сделано в `onPlacementChanged`.

### ⏳ Проекция скоупится по ДАТАМ, а не по сессии
У `schedule_view` нет `session_id`, поэтому `deleteByPeriod` при генерации сносит строки **всех**
сессий с пересекающимися датами (в базе есть легаси-сессия без периода). Побочный эффект: сверка
`projection-health` будет честно показывать по такой сессии «не спроецировано». Правильно — завести
`session_id` в проекции и скоупить по нему.

### ✅ Накопление архивных сессий — решено
Чистка повешена на генерацию (`purgeOldArchivedSessions`), а не на `@Scheduled`: приложение работает
непостоянно, cron на таком профиле ненадёжен. Порог — `schedule.session.archive-retention-days`.
С миграции 017 её каскад доводит удаление до конца: раньше строки проекции удалённых архивных
размещений могли остаться сиротами.

## Производительность: что известно по замерам

Мерили 2026-07-12 (`⏱`-логи + `hibernate.generate_statistics`, сессия на 1075 размещений).
Полные цифры и решения — в [FOLLOWUPS.md](FOLLOWUPS.md).

- Чтение сетки `/query/all` — один индексированный SELECT, ~55 мс на 2700 строк (1.35 МБ).
- **Любая подсветка стоит 120–165 мс**, и это почти целиком **пересоздание `ScheduleWorkspace`**
  (загрузка размещений, разворот ограничений, посев занятий). Сам каскад фильтров — **1 мс**.
  Кэш workspace спроектирован, но не реализован.
- `hibernate.default_batch_fetch_size=100` включён — ленивые связи грузятся пачками, классического
  N+1 в посеве нет (~70 запросов, а не ~1000).
